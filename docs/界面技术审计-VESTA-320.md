## 待修复问题

### B01 · [P1] 空白输入框边界对比度不足

- 位置：`web/refinement.css:245`（共享输入样式，边框在248行）；`web/main.tsx:3446`附近的共享表单内容。
- 类别：可访问性。
- 复现：管理登录 → 客户与跟进 → 新增客户，保持公司名称、地区、电话等字段为空且未聚焦。浏览器计算边框为 `rgb(216,222,232)`（`#d8dee8`），内外表面为白色，无阴影或占位文字。9个空文本字段属于该情形。
- 证据：边界对白色对比约 **1.35:1**。标签标识字段含义，但空白编辑区域仍依赖浅边界定位；低视力用户难以辨认可编辑区域。既有“文字低对比度0命中”不覆盖此问题。
- 标准：[W3C WCAG 2.2 SC 1.4.11 非文本对比度](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast)要求识别控件所必需的视觉信息达到3:1。本项限于依赖边界识别的空文本输入，不把所有浅色按钮边框一概判为违规。
- 建议：建立专用控件边界token，提高未聚焦空字段的边界对比；保留已有聚焦反馈，核查错误、禁用和只读状态。建议 `$impeccable harden`。
- 本机证据：`deep.json`的fields、`empty-fields.png`。

### B02 · [P2] 手机导航展开后，键盘焦点仍走背景页面

- 位置：`web/main.tsx:1109`（导航遮罩）、`web/main.tsx:1200`（菜单触发按钮）；`web/refinement.css:1276`（覆盖式遮罩）。
- 类别：可访问性 / 响应式。
- 复现：390×844，管理端“客户与跟进”页；聚焦“打开导航菜单”并按Enter。菜单展开，焦点留在触发器；按Tab后落到背景“使用指引”，没有进入菜单。Escape后 `aria-expanded` 仍为true。
- 证据：背景按钮矩形x=176.58、y=62、宽74、高44；中心命中的是前景品牌链接而非被聚焦按钮。截图显示焦点大部分被侧栏覆盖。必须反向Tab或绕行才能进入导航，或找到遮罩关闭；触摸点击遮罩未覆盖的右侧可以正常收起。
- 标准：键盘焦点顺序及可见性风险；本项按可绕行的交互缺陷记P2，不仅凭Escape缺失就宣称WCAG失败，也不把部分遮挡等同“完全遮挡”。
- 建议：明确采用覆盖式导航交互，打开时将焦点移到当前导航项，避免Tab进入背景，支持Escape收起并返回触发按钮；关闭和跨断点时恢复背景交互。建议 `$impeccable adapt`。
- 本机证据：`deep.json`的menu、`menu-keyboard.png`。

### B03 · [P2] 屏幕主题仍依赖四层CSS覆盖

- 位置：`web/main.tsx:31`–34依次导入style/prototype/parity/refinement；`web/prototype.css:63`附近重复颜色变量；`web/refinement.css:5`起定义屏幕token。
- 类别：主题 / 实现一致性；延续290的A05维护事项。
- 证据：共享按钮与表面现已使用accent、surface等变量，但旧原型规则仍声明自己的ink/muted/green值，登录及状态等变体仍使用直接色值。静态检测命中style.css的Inter，而浏览器实际字体已是Segoe UI/PingFang/Microsoft YaHei，说明仍需理解覆盖顺序才能确定有效样式。
- 影响：后续修改单层颜色容易在其他表面被覆盖或产生遗漏，提升回归和定位成本；当前没有证据证明深色主题损坏，项目也未承诺深色模式，不将其缺失列为问题。
- 建议：先记录有效屏幕规则与打印边界，逐组件归并重复定义，将确有复用的状态/控件颜色补成语义token；每批复核打印和现有浅色统计卡。建议 `$impeccable document` 后 `$impeccable harden`。本项不要求推倒重做视觉方案。
